ChaosBatch

One bad row can hang a Ray batch-LLM job forever. When a single request crashes the vLLM engine, Ray restarts the engine and retries the same row again and again, even with should_continue_on_error on. I reproduced it, measured it across the configurations users are told to try, and built a small guard that fixes it without forking Ray.

▶ Watch the walkthrough · Code & data · issues: #59522, #65862

Why it hangs

Ray Data LLM runs vLLM engines as a pool of actors. Ray 2.59 handles a dead engine (EngineDeadError) by exiting the actor with os._exit(1) so it restarts, then retrying the batch. That cures one-off CUDA errors. But that fatal path runs before should_continue_on_error is checked, so a row that kills the engine every time is retried forever and the job never finishes.

A broken GPU: the job survives, but at a cost

My first guess was that a bad GPU kills the job. It doesn't: healthy engines absorb the work. But on stock Ray the broken GPU crash-loops for the rest of the job, and every crash throws away the batches in flight. The guard detects it with a canary (a harmless warm-up request every fresh engine must answer) and fences the GPU after 2 canary deaths by reserving its slot.

How the guard assigns blame

When an engine dies, every in-flight request fails with it, so the error alone can't say whether a row or the device is at fault. Two cheap experiments settle it:

  • Canary. If the warm-up request kills a fresh engine, no real row was involved, so the device is at fault and gets fenced.
  • Isolate. Rows in flight during a death become suspects and are re-run one at a time. A row that is alone in flight for 2 deaths is the poison: it's written out as an error row and the job carries on.

Blame state lives in a Ledger actor pinned to the head node. If the guard can't reach it, it behaves exactly like stock Ray, so a safety layer can't become the thing that breaks the job.

Mistakes caught along the way

  • I first guessed a bad GPU kills the job. It doesn't, so the GPU fence is measured against wasted restarts, not crashes.
  • The guarded engine skipped transient-fault injection at first, which made it look better than it was. Fixed, and the matrix re-run.
  • A node-loss test removed the node after the job had already finished. The timing was fixed.
  • The guard caused one failure stock Ray didn't have: its Ledger was on the removed node. It's now pinned to the head node and every call is fail-safe, and 9 of 9 repeat runs passed.
